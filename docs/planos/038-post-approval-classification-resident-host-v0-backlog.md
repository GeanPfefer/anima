## Semântica do cutoff

- `ANIMA_POST_APPROVAL_CLASSIFICATION_SINCE` é um instante ISO-8601 COM fuso (ex.: `2026-10-07T12:00:00Z`); sem fuso, texto livre ou data inválida ⇒ config inválida ⇒ comportamento atual.
- Compara-se o `approvedAt` da aprovação VIGENTE (último `work_approved`): só `approvedAt > since` é elegível. Itens aprovados antes (ou no mesmo instante), inclusive os 8 itens históricos approved sem classificação, ficam intocados.
- Uma re-aprovação posterior ao cutoff (por exemplo readmissão de supervisão) NÃO reclassifica item já classificado (no-op/replay); o cutoff vale para a aprovação vigente.
- O env é lido a cada host-turn pela composition root, mas o Resident Host só enxerga mudança após reinício do processo.

## Limitações conhecidas do V0 (fora do escopo)

- Sucessores de recovery/correção (`resume_from_checkpoint`) e itens de planner/chat continuam exigindo `work prepare-autonomous`; estender é T1/lineage, sobre o mesmo módulo.
- O módulo não distingue o autor da aprovação (`approval` não carrega autor). Aprovações `system`/`autonomous_policy` existem só historicamente (2 eventos em ago/2026) e `auto-approval.ts` não tem chamador de produção; registrar como risco aceito.
- Classificar torna o item elegível à fila; a primeira volta do Host o leva a `blocked` aguardando `work supervise` (comportamento atual para qualquer item classificado). Escolher o modo manual depois do approve deixa de ser praticável com a ativação ligada.

6. Controles negativos opcionais: um item aprovado de origem fora da allowlist e/ou anterior ao cutoff permanece sem classificação.
7. Parar o Host. Qualquer `work supervise` para testar continuidade é checkpoint separado e não é necessário para provar a classificação pós-aprovação.
