# Backlog dedicado — Self-Dev CLI V1: Recovery governado de candidato com defeito real (SDC-03)

Documento de backlog canônico com UM único candidato. Terceiro self-development terminal-first do ANIMA:
o próprio ANIMA (backlog → materializer → aprovação → classificação → roteamento → claim → worktree →
Claude Code real → gate/escopo → evidências → Verifier → review) cria o caminho governado para recuperar um
work item `failed` por DEFEITO REAL DO CANDIDATO, preservando o checkpoint já produzido. O materializer
canônico lê só o documento apontado; este arquivo não altera os documentos 009–015 nem nenhum outro backlog.

Motivo factual (SDC-02, item 7a6743b0-…, attempt 478b667e-…, candidato d6d6323, base 6f7577f): o gate 1
falhou por defeito de código de produção (`work-reference.ts`, TS2532), o Codex executou normalmente (sem
defeito de harness, governor ou ambiente), o candidato tem 10 arquivos (+324/-50) dentro do escopo, a falha é
`retryable=false` e o orçamento de attempts está esgotado (1/1). O `work replan` atual NÃO se aplica: exige
exatamente 1 arquivo de teste (`not_minimal_test_unit`), `coder_backend='ollama'`, saldo de attempts restante
(`replan_budget_exhausted`) e o diagnóstico fechado `test_code_incorrect`. `authorize_harness_fix_recovery`
exige falha `retryable=true`, defeito de harness e NÃO preserva checkpoint. Nenhum dado do SDC-02 pode ser
alterado para "caber": este item é a PRIMEIRA unidade que o SDC-03 deve tornar recuperável, mas NÃO é cobaia
da implementação (a recuperação do SDC-02 é um ato humano posterior, depois de review/aceite/integração do SDC-03).

Decisão humana de executor DESTE bootstrap: `claude-code` (a tarefa atravessa contratos de recovery, core,
SQL/RPC, lineage, orçamento, checkpoint/resume e CLI). Isto NÃO é política fixa de preferência.

Fora do SDC-03 (NÃO tocar): seleção persistida de executor, `work run`, `work create`, referências legíveis,
integração governada F2, frontend, publicação, correção manual do SDC-02, fuzzy matching, evidência operacional
