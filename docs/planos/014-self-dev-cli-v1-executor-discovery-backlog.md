## SDC — Self-Dev CLI V1

### SDC-01 — Executor discovery, readiness e recommendation pela CLI

- **Status:** not_started
- **Objetivo:** Permitir que o humano consulte pelo terminal, com `anima work executors <id> [--json]`, os executores de coding de um work item: quais backends existem, quais estão utilizáveis agora, quais são elegíveis, por que algum está indisponível, qual o ANIMA recomenda e a justificativa determinística. Unidade 100% READ-ONLY: descobre, sonda, recomenda e exibe; NÃO persiste nada, NÃO escolhe executor, NÃO inicia attempt. Regra no código compartilhado (`apps/web/lib/work-orchestration`), nunca só na CLI. Reutilizar `CoderProvider`/`WORKTREE_CODER_BACKENDS`/`coderBackendId` de `coder-backend.ts`, `readExecutionContract` de `executor-selection.ts`, `resolveCodexCliConfig`/`buildCodexCliEnvironment`, `resolveClaudeCodeConfig`/`buildClaudeCodeEnvironment`, `resolveOllamaCoderRuntimeConfig` e `runProcess` de `worktree.ts`. Entregar: (1) `executor-discovery.ts`: módulo PURO (sem I/O, sem node:*), com tipos e `projectExecutorCandidates({ contract, observations })` + `recommendExecutor(candidates, contract)`; (2) `executor-readiness.ts`: seam de readiness com TODAS as dependências injetáveis (runner de processo, existência de arquivo, plataforma, env, GET HTTP do Ollama), `probeExecutorReadiness(provider, deps)` e `probeAllExecutors(deps)`; (3) CLI: comando `work executors <id> [--json]` em `args.ts` (uso: exatamente um id, sem `--reason`), runner `runWorkExecutors` em `app.ts` (lê o item por `getItem`, deriva o contrato com `readExecutionContract`, sonda, projeta; payload `kind: 'work-executors'` com `workItemId`, `state`, `proposalVersion`, `contractBackend`, `observedAt`, `candidates`, `recommendation`), renderização humana em `render.ts`, dispatch em `anima.ts` e linha de ajuda no `USAGE`; (4) documentar o comando em `apps/web/cli/README.md`. CANDIDATO (campos mínimos, só fatos): `provider`, `backendId` (`provider:model`), `displayName`, `availability` (`ready`|`unavailable`|`unknown`), `eligibility` (`eligible`|`ineligible`), `reasonUnavailable` (código estável ou null), `reasonIneligible` (código estável ou null), `model` (do contrato quando o provider coincide, senão o default do backend) e `costClass` (`local` para ollama, `subscription` para codex-cli e claude-code, `paid_api` para openai, `unknown` para deepseek-harness). Sempre listar os cinco providers de `WORKTREE_CODER_BACKENDS`, em ordem estável. Observação ausente ⇒ `unknown` com `reasonUnavailable: 'readiness_not_probed'`. READINESS: codex-cli = executável nativo resolvido por `resolveCodexCliConfig` (wrapper .cmd/.bat/.ps1 ⇒ indisponível), `--version` com exit 0 e `codex login status` com exit 0 indicando login por assinatura; claude-code = `resolveClaudeCodeConfig`, `--version` com exit 0, `claude auth status` retornando JSON com `loggedIn === true`, e no Windows Git Bash localizável (variável `CLAUDE_CODE_GIT_BASH_PATH` ou derivado do git no PATH do filho), ambos com o ambiente allowlisted dos respectivos `build*Environment`; ollama = `resolveOllamaCoderRuntimeConfig` e, quando resolvido, GET injetável de `<url>/api/tags` com timeout curto (falha de rede ⇒ `unavailable`, config inválida ⇒ `unavailable` com o motivo); openai = NUNCA chamar a API: sem chave configurada ⇒ `unavailable` (`openai_api_key_absent`); com chave ⇒ `unknown` (`paid_authority_required_per_item`), porque a authority paga é humana e por item; deepseek-harness = `eligibility: ineligible`, `availability: unavailable`, `reasonUnavailable: 'parked_not_operational'` (não fingir readiness). Nunca ler nem imprimir segredos, tokens, e-mail ou organização: expor só booleanos, códigos estáveis e a versão. Timeouts curtos e limitados em todo probe. RECOMENDAÇÃO (determinística, sem LLM, sem score numérico): considerar só candidatos com `availability === 'ready'` e `eligibility === 'eligible'` (`unknown` nunca é recomendado); se o `contractBackend` declarado no contrato aprovado estiver entre eles, recomendá-lo (regra `contract_declared`); senão ordenar por classe de custo (`local` < `subscription` < `paid_api`) e desempatar pela ordem do registry (regra `local_first`); a recomendação traz `provider`, `backendId`, `rule` e `reason` textual derivada da regra, e `fallback` explícito (o próximo elegível pronto pela mesma ordenação, ou null). Sem candidato pronto ⇒ `recommendation: null` com `reason: 'no_ready_candidate'` e a lista dos motivos por candidato. A recomendação reflete apenas readiness, elegibilidade e custo, e o texto deve dizer isso: NÃO afirma adequação do modelo à tarefa. O comando termina com exit code 0 mesmo sem recomendação; item inexistente segue o erro operacional já existente. O comando NUNCA escreve em banco, NUNCA grava evento, NUNCA cria worktree, NUNCA inicia coder e NUNCA muda o contrato. Testes OBRIGATÓRIOS, todos sem chamada externa real (probes e runners injetados): registry/candidates (cinco providers, ordem estável); ready/unavailable/unknown e `reasonUnavailable`; recomendação por `contract_declared`, por `local_first`, fallback, desempate estável e determinismo (mesma entrada ⇒ mesma saída); nenhum backend disponível; Codex ready/not-ready (sem executável, wrapper, `--version` falha, não logado) e Claude ready/not-ready (sem Git Bash no win32, não logado, JSON inválido) com probes injetados; openai sem chave, openai com chave (`unknown`, nunca chama rede); deepseek estacionado; que nenhum segredo/e-mail aparece na saída; parse de `work executors` (id obrigatório, extras e `--reason` recusados); saída de texto e `--json` do runner/render com item de contrato claude-code. NÃO alterar `coder-backend.ts`, `executor-selection.ts`, `claude-code-coder.ts`, `codex-cli-coder.ts`, nem criar migration, evento, RPC, estado de espera, `work run`, `work select-executor`, `work create` ou frontend. DISTINÇÃO: que os testes realmente caracterizam o comportamento descrito, que a recomendação é honesta sobre o que não sabe, que nenhum segredo vaza e que nada além do escopo foi tocado são objeto da REVIEW HUMANA final e NÃO são evidência provada por máquina; um PASS do Verifier significa apenas gates focais verdes + typecheck + escopo contido.
