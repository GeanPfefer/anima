### SDC-18 — Native CLI External Failure Diagnostics V0

- **Status:** not_started
- **Objetivo:** NATIVE CLI EXTERNAL FAILURE DIAGNOSTICS V0 (SDC-18). PROBLEMA COMPROVADO: no SDC-17 o Codex CLI terminou com exit 1 por usage_limit_exceeded; o harness perdeu a causa: runNativeCliTurn (apps/web/lib/work-orchestration/native-cli-coder.ts) lança Error(`${label} terminou com exit N: ${diagnostic}`) onde sanitizeNativeCliDiagnostic junta `stderr+stdout`, pega as ÚLTIMAS 8 linhas e depois os PRIMEIROS 600 caracteres (cabeça de caracteres sobre cauda de linhas: remove justamente o fim, onde está o erro terminal), e worktree-executor.ts ainda aplica clip(mensagem, 120) em `O backend de código falhou: …`; o sinal persistido fica `code=execution_failed`, e recovery-assessment/recovery-decision classificam `unknown`. A causa real só existia no rollout local do Codex (codex_error_info), que NÃO pode ser lido em runtime. OBJETIVO: persistir, no sinal `error` do executor worktree com backend codex-cli, uma causa externa SANITIZADA e tipada `nativeCliFailure`, mantendo o `code` existente (`execution_failed`) e o histórico válido. REUSE BEFORE BUILD: seguir o padrão de `investigationFailure` (SDC-16) em packages/core/src/work-orchestration/work-executor-contract.ts (tipo V1 fechado, parser fail-closed, campo opcional no sinal `error`, validação no transcript) sem migration (executor_signal é JSONB genérico). SHAPE (V1, fechado, sem texto livre): `nativeCliFailure = { version: 1, category, exitCode: number inteiro, sessionId?: string }` com `category` ∈ `usage_limit_exceeded` | `rate_limit_exceeded` | `unauthorized` | `provider_unavailable` | `unknown_native_cli_failure`. Somente categorias que o runtime consegue distinguir; qualquer causa não reconhecida vira `unknown_native_cli_failure` (preferir o residual a inventar precisão); NUNCA persistir stdout/stderr completos, prompt, última mensagem do agente, tool calls, conteúdo de arquivo, stack, ambiente, tokens ou JSON bruto de rollout; `sessionId` só entra se vier DIRETAMENTE do fluxo do processo (evento `thread.started` do JSONL), com padrão seguro [A-Za-z0-9._:-]{1,80}, sem leitura de ~/.codex/sessions e sem scraping de filesystem. FONTE DA CATEGORIA, em ordem de prioridade: (1) protocolo estruturado: acrescente `--json` aos args do `codex exec` SOMENTE no caminho direto de codex-cli-coder.ts (buildCodexExecArgs sem ai-memory; o caminho wrapped por `ai-memory run`/`exec resume` NÃO muda e cai no residual) e implemente em native-cli-coder.ts um classificador PURO e injetável que lê o stdout JSONL linha a linha (linhas não-JSON ignoradas; tamanho já limitado por runProcess), extrai `thread_id` de `thread.started` e, em `turn.failed` ou `error`, o código estruturado do erro (campo `codex_error_info`/`codex_error_info.<variante>` quando presente; o conjunto fechado do Codex inclui usage_limit_exceeded, rate_limit_exceeded, unauthorized, server_overloaded, http_connection_failed, response_stream_connection_failed, response_stream_disconnected, internal_server_error, context_window_exceeded e other) mapeando: usage_limit_exceeded→usage_limit_exceeded; rate_limit_exceeded→rate_limit_exceeded; unauthorized→unauthorized; server_overloaded, http_connection_failed, response_stream_connection_failed, response_stream_disconnected, internal_server_error→provider_unavailable; qualquer outro código→unknown_native_cli_failure; (2) SOMENTE se o JSONL trouxer o erro sem código estruturado, um parse de texto FECHADO e documentado do campo `message` do evento (nunca da saída humana ampla), limitado a um marcador exato para usage limit; AVISO DE VERIFICAÇÃO: o formato exato do evento de falha em `exec --json` para erros do provider NÃO foi capturado ao vivo (só o rollout foi observado); portanto os testes usam fixtures sintéticas e a prova viva é a futura falha real, NÃO consumir quota para provar; documente no código quão estável é cada fonte. Exit 0 ⇒ nenhum nativeCliFailure; exit ≠ 0 sem causa reconhecida ⇒ `unknown_native_cli_failure` com exitCode (fallback genérico, sem categoria falsa); cancelamento e timeout (`[runner_timeout]`) permanecem exatamente como hoje e NÃO ganham nativeCliFailure. ENTREGA: (a) native-cli-coder.ts: novo erro tipado (subclasse de Error com `nativeCliFailure` readonly, mensagem compatível) lançado por runNativeCliTurn quando exit ≠ 0, aceitando um classificador opcional por adaptador (claude-code-coder.ts NÃO é alterado e continua igual); DIAGNÓSTICO HUMANO: corrigir a menor parte segura localmente em sanitizeNativeCliDiagnostic (sem alterar summarizeCommandOutput compartilhado com gates): preservar a CAUDA final (últimos ~600 caracteres das últimas 8 linhas) em vez da cabeça, mantendo redaction;
