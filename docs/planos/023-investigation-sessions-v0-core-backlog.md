## Evidência empírica prévia (probes descartáveis, 2026-10-05, repositório temporário fora do ANIMA)

- Codex CLI 0.160.0, Windows nativo: `codex exec --sandbox read-only -c approval_policy=never --ephemeral --cd <repo> --output-schema <schema> -o <saida>`
  NEGOU escrita pelo SO ("acesso negado", incluindo `git show --output=<arquivo>`); o controle `--sandbox workspace-write` gravou. Leitura
  FORA do cwd é permitida (read-only ≠ confidencialidade: arquivos do disco, inclusive segredos em arquivo, são legíveis).
  `--output-schema` (schema estrito: todas as propriedades em `required`, `additionalProperties:false`, opcionais como união com `null`)
  + `-o` devolveram JSON conforme o schema. `--json` emite eventos `command_execution` auditáveis (não necessário no V0).
- Claude Code 2.1.286: o perfil SEM Bash (`--tools Read,Glob,Grep`) é estruturalmente somente-leitura; `--permission-mode plan` NÃO é enforcement
  (o modelo apenas se recusa por escolha); o perfil com Bash por allowlist (`Bash(git show:*)`) FOI CONTORNADO por `git show --output=<arquivo>`
  (arquivo criado); `--strict-mcp-config` é necessário (ferramentas MCP vazaram para a sessão aninhada); `--json-schema` devolve `structured_output`
  e `permission_denials` registra as tentativas negadas. Conclusão: o primeiro candidate usa só Codex; Claude Code fica para depois, sem Bash.
- A segurança NÃO pode depender só do CLI: a verificação pós-execução do host é obrigatória (o caso do `git show --output` foi detectado por `git status`).

PASSO 1 (antes de editar, só leitura; REUSE antes de BUILD): leia `executor-selection.ts` (`resolveExecutorRoute`), `planned-project-classification.ts`, `autonomous-authorization.ts`, o contrato de execução/sinais em `work-executor-contract.ts`, `verifier-opinion.ts` (core e web), `mandated-verification.ts` e as RPCs `finish_work_execution`/`record_verifier_opinion` e registre no resultado, SEM alterar esses arquivos fora do escopo, onde o pipeline PRESUME programming (classificação exige capability programming e permissões exatamente `workspace_read`+`workspace_write_isolated`; gatilho SQL por attempt exige decisão de roteamento e classificação; candidatos de rota declaram `capabilities: ['programming']`; autorização recusa `capability_not_programming`; o lane mandatado é acoplado a evidência de programming): esse mapa alimenta o SDC-11. Restrições fixas do PASSO 1: o lane `verifier_requirement=advisory` leva o resultado a `review` sem Verifier obrigatório; NÃO altere SQL, NÃO crie migration, NÃO use o lane mandatado, e o caminho de programming deve permanecer idêntico. PASSO 2 — CLASSE DE EFEITO enforceável (módulo core puro, fail-closed): o campo `execution_spec.effect_class` (`read_only`; ausência ⇒ comportamento atual, mutante); valor desconhecido é inválido (nunca vira mutante por default); SEMÂNTICA: `effect_class=read_only` significa que a attempt NÃO possui autoridade para mutar o objeto governado (o snapshot do repositório, os refs e o estado do ANIMA) e que a ausência de mutação é VERIFICADA pelo host (PASSO 5); ele NÃO significa que o executor seja tecnicamente incapaz de ler fontes fora do escopo declarado. Duas propriedades distintas: (A) isolamento de efeito/mutação — prometida e enforçada no V0 (permissões só de leitura, sandbox `read-only` do CLI e verificação do host); (B) isolamento de confidencialidade/fonte de leitura — NÃO prometida no V0 (probe: o Codex em read-only leu um arquivo fora do cwd); o escopo de fontes é declarado, entra no prompt e fica sujeito a review/auditoria, mas não é fronteira de confidencialidade garantida, e NÃO se constrói sandbox adicional agora. `read_only` exige permissões somente de leitura (`workspace_read`, sem `workspace_write_isolated` nem equivalentes de escrita) e o adapter de investigação; um item mutante nunca pode ser executado pelo adapter de investigação; funções puras para ler a classe de uma intent e checar coerência com permissões/executor. PASSO 3 — RESULTADO ESTRUTURADO (contrato core puro, sem I/O): `InvestigationResultV1` = findings[{statement, status ∈ established|inferred|undetermined, evidence[]}], gaps[], outcome ∈ conclusive|partial|inconclusive. Evidência tipada e resolvível, só dois tipos no V0: `file_at_commit` {commit 40-hex, path relativo seguro, linhas opcionais} e `commit` {commit}. Regras: `established` e `inferred` exigem evidência; `undetermined` pode não ter; `partial` e `inconclusive` exigem `gaps` não vazio (um "não encontrei" honesto declara o que faltou); `conclusive` exige ao menos um finding; limites de tamanho e quantidade; recusa de conteúdo sensível (reuse a régua existente de sanitização); a forma de transporte para o Codex é o schema estrito validado no probe (opcionais como união com null), convertida para a forma normalizada, e o módulo expõe esse schema. A narrativa (`summary`) é RENDERIZAÇÃO da estrutura, nunca substituta. O resultado viaja no sinal terminal de resultado do executor (campo próprio opcional `investigation` em `work-executor-contract.ts`, ao lado de e NUNCA junto a `worktreeHandoff`; `finish_work_execution` já persiste o sinal inteiro, e `handoffReference` não pode ser caminho absoluto) — sem migration. PASSO 4 — EXECUTOR: um adapter novo `investigation-v1` que implementa `WorkExecutorAdapter` e reutiliza por IMPORT, sem alterar, o que o Codex CLI já tem: resolução de executável (`ANIMA_CODEX_CLI_PATH`), ambiente por allowlist (`buildCodexCliEnvironment`), `runProcess`, deadline e cancelamento. Perfil somente-leitura: `exec --sandbox read-only -c approval_policy=never --ephemeral --cd <snapshot> --output-schema <arquivo-temporário> -o <arquivo-temporário>`; o executor NUNCA recebe EDIT nem fluxo de candidate, e o adapter recusa (`invalid_request`) qualquer pedido cujas permissões incluam escrita ou cuja classe de efeito não seja `read_only`. O objeto observado é um SNAPSHOT: `git worktree add --detach` no `base_sha` autorizado (sem criar branch), descartado ao fim; o prompt determinístico traz a pergunta, o escopo declarado de fontes (esse snapshot, como INSTRUÇÃO e não como fronteira de leitura), o contrato de saída e a instrução de citar evidência `arquivo@commit:linhas`. PASSO 5 — VERIFICAÇÃO DO HOST, antes de emitir o resultado; o host afirma SOMENTE propriedades concretas e observáveis: (A) o snapshot governado permaneceu sem alterações produzidas pelo executor — `git status --porcelain=v1 --untracked-files=all --ignored` do snapshot vazio ao fim da attempt; (B) o HEAD do snapshot continua no `base_sha` e destacado (sem symbolic-ref); (C) nenhum ref de resultado proibido foi produzido — nenhuma branch sob `anima-work/` nem ref cujo nome contenha o `attemptId` existe depois da attempt (comparado antes/depois pelos nomes proibidos, de modo que a atividade concorrente do operador no checkout vivo não gera falso positivo; justifique no teste a escolha dos checks); (D) cada referência de evidência RESOLVE no repositório (commit existe; path existe como arquivo naquele commit; linhas dentro do arquivo); (E) a estrutura mínima do PASSO 3 é válida. O host NÃO afirma ausência de mutações arbitrárias no filesystem, ausência de efeitos externos ou de rede, nem ausência de leitura fora do snapshot. Violação de A–C ⇒ o adapter emite `error` `execution_failed` não retryable; D ou E falhos ⇒ `error` retryable. Um resultado `inconclusive` estruturalmente válido NÃO é falha e é emitido como resultado. A verdade semântica dos findings NÃO é julgada automaticamente: é matéria da review humana. ## Prova viva do adapter pós-aceite (ato do operador, FORA do candidate; não escreve código do ANIMA)

Depois do aceite e da integração humana do SDC-10, o operador roda um script de sessão (não commitado) que instancia o
`investigation-v1` com o Codex real sobre um snapshot do dev e imprime os sinais emitidos, sem banco, sem Claude Code, sem web, sem
browser e sem authority paga:

1. P1 (conclusiva): pergunta pequena e determinística respondível só com READ/SEARCH. Sugestão: "Quais valores de
   `execution_spec.executor` o `resolveExecutorRoute` reconhece no snapshot e que erro devolve para um executor desconhecido?".
   Esperado: resultado com findings + evidência que resolve; nenhum arquivo/branch/ref alterado.
2. P2 (inconclusiva honesta): pergunta cuja resposta NÃO está no repositório (ex.: custo de uma attempt, que vive no banco).
   Esperado: `partial` ou `inconclusive` com `gaps`, emitido como resultado (não como falha).
3. P3 (mutação deve falhar): pergunta adversarial que induz o executor a tentar escrever. Esperado: o sandbox nega e/ou a
   verificação do host rejeita; nenhum arquivo, branch ou ref alterado; se houver mutação, a attempt falha.
